# Pipeline Audit & Recommendations — Where the Real Prompt-Engineering Lever Lives

> **TL;DR:** The DSPy signature files in `dspy_components/tasks/**/signatures.py` are **not hand-written** — they are auto-generated by an LLM call. The real lever for prompt quality is `core/generators/prompts/signature_prompt.md` (the meta-prompt). Upgrading individual signature files is whack-a-mole; upgrading the meta-prompt fixes every future generation at once.

---

## 1. The actual pipeline (end-to-end)

```
User uploads form spec (JSON of fields)
         ↓
LangGraph workflow (core/generators/workflow.py)
         ↓
Node 1: decompose_form()                    ← LLM call · prompts/decompose_form.md
         ↓
Node 2: DecompositionValidator              ← coverage / DAG / pipeline checks
         ↓
Node 3: HumanReviewHandler (optional)
         ↓
Node 4: SignatureGenerator.generate_signature()
        ↳ LLM call · prompts/signature_prompt.md   ← THE PROMPT THAT WRITES YOUR PROMPTS
        ↳ Structured output → SignatureSpec → Python code
         ↓
Node 5: ModuleGenerator                     ← template-based, NO LLM
         ↓
Node 6: Files written to dspy_components/tasks/dynamic_<id>_<name>/
         ↓
At runtime: AsyncModuleExtractor wraps each ChainOfThought call,
            pipeline runs in DAG order (parallel within a stage)
```

### Key files

| Step | File | Role |
|---|---|---|
| Workflow orchestrator | `core/generators/workflow.py` | LangGraph StateGraph, all nodes |
| Decomposition prompt | `core/generators/prompts/decompose_form.md` | Splits form into atomic signatures |
| **Signature meta-prompt** | **`core/generators/prompts/signature_prompt.md`** | **Writes every `desc=` string** |
| Signature generator | `core/generators/signature_gen.py:33` | Loads meta-prompt, calls LLM, gets `SignatureSpec` |
| Module generator | `core/generators/module_gen.py` | Pure template — no LLM |
| Validators | `signature_validator.py`, `module_validator.py`, `decomposition_validator.py` | Structural checks |

## 2. Audit findings (signature quality)

### Files audited

- `backend/dspy_components/utility_signatures.py`
- `backend/dspy_components/tasks/index_test/signatures.py`
- `backend/dspy_components/tasks/reference_standard/signatures.py`
- `backend/dspy_components/tasks/patient_population/signatures.py`
- `backend/dspy_components/tasks/outcomes_study/signatures.py`
- `backend/dspy_components/tasks/missing_data_study/signatures.py`

### Class docstring quality

Most class docstrings reference **form questions** ("Form Question 11") and give brief operational guidance, but they are **not anchored to QUADAS-2 / STARD domains by name**. Words like "review bias", "verification bias", "disease progression bias" appear in passing (e.g., `ExtractBlindingReferenceStandard`, `ExtractTimeInterval`) but no docstring names a QUADAS-2 domain (Patient Selection, Index Test, Reference Standard, Flow & Timing) or signaling question.

**Verdict:** task-anchored, not methodology-anchored.

### `desc=` quality on OutputFields

Mixed. Most fields include a JSON schema, 2–3 rules, and 2–3 examples — better than one-liners but inconsistent.

**Weak spots:**
- No "common confusion" callouts (e.g., assessor-blinding-to-collection vs examiner-blinding-to-reference)
- No edge-case rules for ambiguous reporting (e.g., when only one CI bound is given, when sensitivity is reported per-subgroup)
- No domain warnings (e.g., "do not infer TP/FP from sensitivity — extract only if explicit")
- Combine* signatures have terse `desc` (just "JSON from X")
- `utility_signatures.py` fields are one-line generic

### Top-3 signatures most at risk of field confusion

1. **`ExtractAssessorTrainingAndBlinding`** — `tasks/index_test/signatures.py:260` (output desc lines 278–301). Three near-identical fields (`assessor_training`, `assessor_blinding`, `examiner_blinding`) where blinding-to-sample-collection vs blinding-to-reference-standard is constantly confused.

2. **`ExtractConfusionMatrixMetrics` + `ExtractSensitivitySpecificity`** — `tasks/outcomes_study/signatures.py:69` and `:118`. TP/FP/FN/TN definitions are correct but no rule against back-computing from sensitivity/PPV; sensitivity vs PPV and specificity vs NPV are easily swapped.

3. **`ExtractPositivityThreshold` (reference_standard)** — `tasks/reference_standard/signatures.py:134`. Four overlapping selected-flags (oral_cavity_cancer, OPMD, SCC, other) with substantial clinical overlap (SCC is a subset of oral cavity cancer). No disambiguation rule. Same name collision exists with `ExtractPositivityThreshold` in `tasks/index_test/signatures.py:215`.

### Pipeline call sites (where signatures get wrapped)

All wrapped in **`dspy.ChainOfThought(...)`** inside `modules.py` siblings:

- `tasks/index_test/modules.py:27,53,76,99,122,147,170,194,214`
- `tasks/reference_standard/modules.py:25,48,71,96,123,143,163`
- `tasks/patient_population/modules.py:24,53,79,110,140,169`
- `tasks/outcomes_study/modules.py:24,44,67,111,155,202`
- `tasks/missing_data_study/modules.py:22,45,68,88`

### Few-shot demos / optimizer status

**None configured in the production pipeline.**

- `demos=[]` is the default throughout the production pipeline — no few-shot demos are configured
- No `MIPROv2`, `BootstrapFewShot`, `GEPA`, or `.compile()` of a DSPy program anywhere in `backend/dspy_components`
- The only `.compile()` calls are LangGraph workflow compiles, unrelated
- Docs (`docs/SYSTEM_AUDIT.md:434`, `EMNLP_2026_eval_plan.md:279`) explicitly call out that the system uses DSPy but **skips the optimizers entirely**

**Implication:** because no optimizer is wired up, every prompt-quality gain has to come from hand-authored `desc=` strings. Currently the only knob.

## 3. The real fix (what the meta-prompt is missing)

`signature_prompt.md` currently teaches the generator LLM:

| Currently teaches | Status |
|---|---|
| JSON schema, examples | ✓ |
| "NR" convention | ✓ |
| Source grounding (`value` + `source_text`) | ✓ |
| One field per extracted value | ✓ |
| Methodology anchoring (QUADAS-2 / STARD / CONSORT) | ✗ |
| "Common confusion:" callouts for sibling fields | ✗ |
| "Edge cases:" blocks for known reporting variants | ✗ |
| "Do not infer / back-compute / round" rules for numerics | ✗ |
| Surfacing domain warnings inside `desc` | ✗ |

Every signature the system generates inherits these gaps from this single file.

---

## 4. Recommended changes

### Primary change

**Upgrade `core/generators/prompts/signature_prompt.md`** with a new section `Domain-Aware Description Quality` (placed before the existing `CRITICAL REQUIREMENTS` block). It should instruct the generator LLM to:

1. **Anchor the class docstring** in the methodology framework named in the form spec (QUADAS-2 / STARD / CONSORT / PRISMA), not just "Form Question N".
2. **For semantically-close sibling fields** (two blinding fields, sensitivity vs PPV, TP vs sensitivity), append a **"Common confusion:"** block to `desc=` that names the sibling and gives the distinguishing rule.
3. **For known reporting variants** (1-spec → spec; per-patient vs per-lesion; CI bound conversions), append an **"Edge cases:"** block.
4. **For any numeric extraction**, include a "do not infer / do not back-compute / do not round" rule.
5. Add 1–2 worked examples in the meta-prompt showing what a `desc=` with confusion + edge-case blocks looks like.

### Optional secondary change

Update `core/generators/prompts/decompose_form.md` so the decomposer surfaces a `semantically_close_groups` hint in the enriched signature payload — the signature generator can then deliberately target those groups with confusion blocks.

### Files NOT changed

- `dspy_components/tasks/**/signatures.py` — outputs of the generator. They will improve organically as forms are re-generated. A separate one-off regeneration sweep can be discussed if desired.
- `signature_gen.py` — the Python code reads the prompt as a template; no code change needed.
- `models.py` — `SignatureSpec` already accepts arbitrary description strings; no schema change needed.

---

## 5. Out of scope for this change (follow-ups)

- **BootstrapFewShot / MIPROv2 wiring** — biggest long-term lever. Requires building a small ground-truth set + compile script. Separate task.
- **Retroactive regeneration** of all existing `dynamic_*/signatures.py` directories using the upgraded meta-prompt. One-off sweep.
- **Renaming the duplicate `ExtractPositivityThreshold`** collision between `tasks/index_test/` and `tasks/reference_standard/`. Separate refactor.

## 6. Verification plan

1. **Unit test the new meta-prompt locally:**
   - Pick one form spec from `data/` or `forms/` (e.g., the index-test form).
   - Run `SignatureGenerator(model_name).generate_signature(enriched_sig)` for one signature with the upgraded prompt.
   - Inspect generated `desc=` strings — should contain "Common confusion:" / "Edge cases:" blocks where applicable.

2. **ChatAdapter inspection:**
   - Instantiate `ChatAdapter()` and call `.format()` on the signature to confirm upgraded `desc=` flows correctly into the system prompt.

3. **End-to-end:**
   - Trigger the workflow via the production entry point (`WorkflowOrchestrator`).
   - Generate a fresh `dynamic_*_TestForm` directory.
   - Diff its `signatures.py` against an old equivalent.

4. **Regression check:** existing `SignatureValidator` and `DecompositionValidator` tests should still pass — we only enrich descriptions, structure is unchanged.

---

## 7. Why this matters (decision rationale)

- **Day-1 hand-crafted Claude prompt** is slightly better than DSPy auto-prompt.
- **DSPy auto-prompt + good `desc=` + optimizer** beats hand-crafted by a wide margin.
- **DSPy auto-prompt without good `desc=` and without optimizer** (current state) leaves both levers unused.

We pick the meta-prompt upgrade first because:
- One file change, propagates to every future generation
- No infrastructure work, no training data needed
- Unblocks the optimizer work later (better baselines = faster optimizer convergence)
